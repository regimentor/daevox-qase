# Дизайн авторефреша API-сессии

Этот документ фиксирует согласованный контракт реализации для `.scratch/api-session-auto-refresh/issue.md`.

## Текущее состояние

- Access-токен хранится только в памяти процесса вкладки.
- Refresh-токен хранится в `localStorage`.
- Apollo link реагирует на GraphQL `UNAUTHENTICATED`, вызывает refresh через отдельный Apollo Client и повторяет операцию один раз.
- `RefreshCoordinator` объединяет только одновременно выполняющиеся refresh внутри одной вкладки.
- Любая ошибка refresh сейчас очищает сессию.
- Вкладки не координируются, хотя backend использует одноразовые refresh-токены и глобально отзывает активные сессии пользователя при reuse.

## Состояние сессии во вкладке

В памяти вкладки хранится логическое состояние:

```text
accessToken: string | null
accessTokenExpiresAt: timestamp | null
generation: monotonic number
```

`generation` изменяется при принятии нового набора токенов и при завершении сессии. Исходная GraphQL-операция запоминает поколение, с которым была отправлена.

Access-токен не сохраняется постоянно в `localStorage`. Refresh-токен остаётся общим для вкладок по существующему storage contract. Служебные lease/generation/message записи не должны содержать секреты дольше, чем требуется для доставки межвкладочного события.

## Алгоритм перед запросом

1. Если сессии нет, отправить запрос без refresh.
2. Если access-токен действует ещё не менее 60 секунд, отправить запрос с ним.
3. Если до истечения менее 60 секунд, присоединиться к существующему refresh или попытаться стать его владельцем.
4. При успешном refresh принять новую пару токенов, expiry и поколение, затем отправить исходный запрос.
5. При временной ошибке refresh:
   - если старый access-токен ещё действует, отправить запрос с ним;
   - если он истёк, не отправлять запрос и вернуть временную ошибку без очистки сессии.
6. При окончательной refresh-ошибке завершить сессию во всех вкладках.

## Реактивный алгоритм

При GraphQL `UNAUTHENTICATED`:

1. Не повторять операцию, если она уже имеет retry marker.
2. Не повторять операцию, если ответ содержит `data`.
3. Сравнить поколение отправки с текущим поколением.
4. Если поколение уже изменилось, повторить операцию один раз с текущим access-токеном без нового refresh.
5. Если поколение не изменилось, выполнить или дождаться refresh, затем повторить операцию один раз.

Это ограничивает повтор одним разом и защищает mutation от повторного выполнения после частичного успеха.

## Координация внутри вкладки

Все потребители ожидают один shared promise текущего refresh. Его результат содержит либо новый session state, либо типизированную временную/окончательную ошибку. Завершившийся promise нельзя использовать как постоянный cache: необходимость следующего refresh определяется expiry и поколением.

## Координация между вкладками

Основной путь:

1. Получить origin-scoped `Web Lock` для refresh.
2. До выполнения refresh повторно проверить поколение и expiry: другая вкладка могла уже обновить сессию.
3. Выполнить единственный refresh с актуальным refresh-токеном.
4. Обновить общий refresh-токен.
5. Опубликовать `tokens-updated` через `BroadcastChannel`, включая access-токен, access expiry и новое поколение.
6. Освободить lock.

Ожидающие вкладки подписываются на результат до ожидания lock, чтобы не потерять событие. Сообщения принимаются только при поколении новее локального.

Fallback:

- использовать lease в `localStorage` с уникальным идентификатором вкладки и коротким сроком;
- доставлять эфемерные адресные сообщения через `storage` events и удалять message envelope после доставки;
- перед refresh перечитывать lease, поколение и актуальный refresh-токен;
- после истечения lease разрешить takeover;
- если владелец успел ротировать refresh-токен, но закрылся до публикации access-токена, новый владелец выполняет следующую ротацию с актуальным refresh-токеном.

Точные значения lease timeout и heartbeat выбираются при реализации и закрепляются тестами. Timeout должен быть достаточно коротким для восстановления после закрытия вкладки и достаточно длинным, чтобы обычный refresh не создавал ложный takeover.

## Межвкладочные события

Минимальные события:

```text
tokens-updated
session-ended
token-state-request
token-state-response
```

`session-ended` увеличивает поколение и имеет приоритет над сообщениями старых поколений. Получив его, вкладка очищает access state и Apollo cache. Явный logout также удаляет общий refresh-токен и уведомляет остальные вкладки.

## Классификация ошибок

Окончательные:

- `REFRESH_TOKEN_INVALID`;
- `REFRESH_TOKEN_REUSED`.

Они очищают локальную сессию и распространяют `session-ended`.

Временные:

- network failure;
- HTTP 5xx;
- throttling/HTTP 429;
- неизвестная техническая ошибка, не классифицированная как окончательная.

Они не очищают токены. Скрытая серия retry не выполняется; следующая пользовательская операция может снова инициировать refresh.

## Длительность сессии

Абсолютного предела активной сессии нет. Каждый успешный refresh может продолжать сессию по текущему backend contract. Если refresh не выполнялся 30 дней, существующий refresh TTL завершает неактивную сессию и требует нового входа.

## Проверки

Unit tests должны зафиксировать:

- границу 60 секунд;
- fallback на ещё действующий access-токен;
- запрет отправки с истёкшим токеном после временной refresh-ошибки;
- single-flight внутри вкладки;
- late `UNAUTHENTICATED` и смену поколения;
- максимум один retry;
- отсутствие retry при частичном `data`;
- terminal/transient classification;
- фильтрацию старых межвкладочных сообщений;
- lease takeover и перечитывание refresh-токена;
- распространение logout/session-ended.

Browser/e2e tests должны зафиксировать:

- прозрачный refresh и завершение исходного API-запроса после истечения access-токена;
- конкурентный запрос из нескольких вкладок без reuse и глобального отзыва;
- синхронное завершение сессии во вкладках после logout.

## Неизменяемые границы

- Backend, storage и GraphQL SDL не меняются.
- Generated GraphQL files не редактируются вручную.
- API остаётся authority для authentication и authorization.
- Access-токен не переносится в постоянное browser storage.
- Реализация остаётся внутри допустимых FSD-зависимостей и публичных API slices.
